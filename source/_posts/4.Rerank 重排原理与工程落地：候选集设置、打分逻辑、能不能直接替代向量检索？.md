# Rerank 重排原理与工程落地：候选集设置、打分逻辑、能不能直接替代向量检索？

> 📌 本文基于线上落地**StarRag企业知识库项目**实战总结。很多做 RAG 的同学把 Rerank 当成 “万能特效药”，有的直接拿上万条候选丢给 Rerank，还有人想直接用 Rerank 替代向量检索。本文结合项目踩坑实战，讲清楚 Rerank 底层原理、打分逻辑、候选集大小怎么配置、生产环境工程链路、常见误区，回答高频面试题：Rerank 能不能直接替代向量检索。
> 
> 🔖适合人群：RAG 工程落地开发者、准备大模型应用开发面试、想要分清 Demo 与生产级 RAG 差异的同学。

项目技术栈：`FastAPI + LangGraph + Milvus + BGE‑M3 + BGE‑Reranker‑large + MinIO + MongoDB`

## 前言

在 RAG 链路中，Rerank（重排）是提升检索质量非常关键的一环。网上 Demo 经常简单演示：向量召回一批结果，直接丢给 Rerank 输出 Top‑N。 但上线生产环境之后会踩一堆坑：

1. 候选集给的太大，QPS 暴跌、服务延迟飙升，GPU 资源打满；
2. 候选集太小，把真正相关的文档提前过滤掉，Rerank 再强也救不回来；
3. 搞不清 Rerank 打分逻辑，看不懂输出分数代表什么；
4. 产生误区：既然 Rerank 语义理解能力更强，那是不是可以跳过向量检索，全部文档直接丢 Rerank？

本文结合StarRag项目实战，拆解 Rerank 原理、打分逻辑、候选集工程配置、链路位置、踩坑复盘，解答 “Rerank 能不能直接替代向量检索” 这个高频问题。

## 一、Rerank 重排底层原理与打分逻辑

### 1. 原理

Reranker 属于**交叉编码器（Cross‑Encoder）**。 向量 Embedding 模型（BGE‑M3）是**双编码器（Bi‑Encoder）**：Query 和文档分开编码，得到向量之后做相似度计算。 而 Cross‑Encoder Rerank 是把`[query, document]`拼接成一组 pair，输入模型内部做联合编码，**同时看到问题 + 整篇文档上下文**，输出 0‑1 之间相关性分数。

> Bi‑Encoder：query、文档分开编码 → 速度快，适合海量库做粗召回； Cross‑Encoder：query + 文档成对输入联合编码 → 语义判断精度更高，但**速度慢、算力开销大，不适合海量文档遍历**。

### 2. 打分逻辑（BGE‑Reranker‑large）

输出分数区间`0 ~ 1`：

- 分数越接近 1：query 和文档相关性越高；
- 分数越接近 0：几乎完全不相关。

⚠️重点：**Rerank 的分数是 pair 内部的相对分数，不是全局绝对相似度**。 同一个文档，搭配不同 query，分数会变化；不能拿 0.5 当做普适的全局阈值，阈值要基于自己业务测试集标定。

> 我们StarRag项目经过业务测试，经验阈值：低于 0.3 基本判定为无关；断崖检测使用**绝对差 0.5、相对差 25%**作为截断经验值。

## 二、Rerank 在完整 RAG 链路中的位置

### 存储链路

> Rerank**不参与写入、入库阶段，只作用于查询阶段**，不会生成向量存入向量库。

### 查询链路完整片段

```
用户Query → Query改写
    ↓
BGE‑M3 稠密+稀疏多路并行检索
    ↓
RRF倒数排名融合（粗融合、去重，压缩候选集）
    ↓
【送入Rerank】对每一条 <query‑doc> pair做交叉编码打分
    ↓
按分数降序排序 + 断崖检测动态截断过滤低分
    ↓
过滤之后的候选切片送入LLM生成答案
```

> 💡工程铁律：**Rerank 放在粗召回、RRF 融合之后，做精排，不放在最前面。**

## 三、候选集大小如何设置？生产环境权衡

> 候选集过大：GPU 开销暴涨、延迟升高，QPS 上不去； 候选集过小：真正相关的文档在粗召回阶段就被丢弃，Rerank 没有机会挽救。

### 项目实战配置（StarRag）

1. 多路检索之后，RRF 融合输出**最多保留 20 条本地知识库候选**；再合并 MCP 网页检索结果，整体给到 Rerank 的候选不超过 25 条。
2. Rerank 输出之后，不写死固定 TopK，使用**断崖检测动态截断**：最少保留 6 条，最多保留 15 条。
    - 相邻文档分数**绝对差 0.5 或者相对差 25%**，触发截断，后面全部丢弃；
    - 设置最低门槛：分数低于 0.3 直接丢弃，全部候选都低于 0.3 则触发拒答。

### 候选集设置核心权衡思路

1. 粗召回阶段要保证**召回率优先**：把可能相关的文档尽量捞进来，可以容忍混入噪声；噪声交给 Rerank 过滤。
2. 但是不能无限制放大候选数量：Rerank 每一条 pair 都要跑一次前向推理，候选数量翻倍，推理耗时几乎同步上涨。
3. 离线评测调参：基于自己业务测试集，遍历不同候选数量，观测`context_recall`、服务 P95 延迟两个指标，找到平衡点。
    - 候选增大：context_recall 上升，但延迟、GPU 占用同步上升；
    - 候选缩小：延迟下降，但存在丢失正确文档的风险。

> 误区：直接把上百、几百条候选全部丢进 Rerank，追求 “不漏任何一条”，线上会直接出现性能灾难。

## 四、核心问题：Rerank 能不能直接替代向量检索？

**结论：生产环境不能直接替代，只能作为精排组件。**

### 原因拆解

1. **算力与性能瓶颈** Rerank 是 Cross‑Encoder，推理开销很高。假设知识库几十万 chunk，如果跳过向量检索，把全部文档和 query 组成 pair 送入 Rerank，耗时会爆炸，完全不满足线上接口响应要求。 向量库 Bi‑Encoder 向量检索可以毫秒级在几十万、百万级文档做粗筛。Rerank 不适合做海量库的全库遍历。
2. **分工不一样**

- 向量检索（Bi‑Encoder）：负责大海捞针，从几十万文档中，快速捞出一小批 “有可能相关” 的候选；
- Rerank（Cross‑Encoder）：负责小候选集合里面，做精细的语义甄别，区分哪些真正有用，哪些是噪声。

> 类比：向量检索相当于初试，筛掉绝大多数人；Rerank 相当于复试，只对通过初试的一小批人精细考核。不能直接让几百万全部选手直接进复试。

### 什么场景可以 “近似只用 Rerank”？

只有文档数量非常小，比如几十条以内的小 Demo，才可以把全部文档丢 Rerank；企业级知识库 chunk 达到几万、几十万级别，必须「向量粗召回 + Rerank 精排」组合。

## 五、项目踩坑复盘

1. ❌坑：把上百条候选全部丢入 Rerank，追求不漏文档 ✅后果：GPU 占用飙升，接口 P95 延迟暴涨，QPS 严重上不去。 ✅解决：上游多路召回 + RRF 做粗压缩，控制输入 Rerank 的候选规模。
2. ❌坑：写死固定 TopK，例如固定取 Top‑8 ✅后果：简单问题带入大量噪声；复杂问题证据不足。 ✅解决：Rerank 输出后采用断崖检测动态截断，配合最低相关性阈值过滤低分。
3. ❌坑：直接拿 0.5 当做全局通用过滤阈值 ✅后果：不同 Query 场景分数分布差异很大，硬阈值会误杀有效片段或者放过噪声。 ✅解决：基于业务测试集标定经验阈值，优先用断崖相对差值做截断，辅以 0.3 最低安全门槛。
4. ❌坑：跳过向量检索，想直接全量 Rerank 替代召回 ✅后果：文档量稍微变大，服务完全不可用。 ✅解决：严格遵循「向量粗召回 → RRF 融合 → Rerank 精排」链路。
5. ❌坑：RRF 输出结果不做任何过滤，直接交给 Rerank，包含大量重复切片 ✅后果：浪费 Rerank 算力，重复文档抢占候选名额。 ✅解决：RRF 阶段做文档 id 去重，再送入 Rerank。
6. ❌坑：认为 Rerank 可以修复上游召回完全没命中的问题 ✅后果：正确文档根本没有进入候选集，Rerank 再强也无能为力。 ✅解决：Rerank 只能改善已经进入候选池的文档排序；**不能把没有召回出来的文档凭空变出来。**

## 六、Rerank 使用关键总结

1. Rerank 是 Cross‑Encoder 交叉编码器，做 query‑doc 成对联合编码，语义判别精度高，但算力开销大，适合小候选集精排，不适合海量文档遍历。
2. 分数 0‑1 是 pair 相对分数，不是全局绝对相似度，不能直接拿通用阈值硬套所有业务。
3. 工程链路：多路向量粗召回 → RRF 融合去重压缩候选 → Rerank 重排 → 断崖动态截断过滤低分。
4. 候选集大小是召回率和性能的权衡，要结合测试集指标 + 线上延迟综合确定，不要一味追求越大越好。
5. Rerank**不能替代向量粗召回**，只能对已经捞出来的候选做重排；正确文档如果上游没有被召回，Rerank 救不回来。
6. 不要写死固定 TopK；优先采用断崖检测动态截断，兼顾简单、复杂不同查询场景。

## ✨博客附加：配套面试真题（全部来源于两份原始文档）

> 题干来源：`02‑尚硅谷AI全能开发技术之企业面试真题V1.0.0.docx`、`01‑尚硅谷AI全能开发技术之高频面试题‑V1.16.0.docx`

### Q1：Rerank 重排的底层原理是什么？Bi‑Encoder 和 Cross‑Encoder 区别？BGE‑Reranker 打分是什么含义？

**面试回答：** Rerank 属于 Cross‑Encoder 交叉编码器。

- Bi‑Encoder（例如 BGE‑M3 embedding）：Query、文档分开独立编码，生成向量，之后计算相似度。速度很快，适合海量知识库粗召回。
- Cross‑Encoder（Reranker）：把`query+doc`拼接成对，输入模型做联合编码，同时看到问题和整篇文档，语义相关性判断精度更高；缺点推理算力开销大，速度慢，不适合海量文档遍历。

BGE‑Reranker‑large 输出分数范围 0~1，分数越高代表这一组 query‑doc 相关性越高。 ⚠️这个分数是**pair 内相对分数，不是全局绝对相似度**。同一个文档搭配不同 query，分数会变化，不能直接拿 0.5 当做所有业务的通用全局阈值。我们项目业务经验，低于 0.3 基本视为无关。

### Q2：你们项目 Rerank 放在链路哪个位置，上游做了什么处理再送入 Rerank？

**面试回答：** 不会直接把原始多路召回结果直接丢 Rerank。 链路顺序：用户 query 改写 → BGE‑M3 稠密稀疏多路并行检索 → RRF 倒数排名融合、做文档去重，压缩候选集合；再合并 MCP 网络检索结果之后送入 Rerank。 上游 RRF 的作用是廉价粗融合、去重，把候选数量降下来，控制送入 Rerank 的文档条数，防止候选太多导致 GPU 压力大、接口延迟飙升。

### Q3：送入 Rerank 的候选集是不是越大越好？候选集大小怎么权衡？

**面试回答：** 不是越大越好。 候选集大：可以提升`context_recall`，更不容易漏掉潜在相关文档；但是 Rerank 每一条 pair 都要做推理，候选数量上涨，GPU 消耗、接口 P95 延迟会同步上涨，线上 QPS 会被限制。 候选集太小：会出现正确文档在粗召回阶段就被丢弃，Rerank 再强也没有机会处理。

我们项目 RRF 融合后本地候选最多 20 条，加上 MCP 结果整体给到 Rerank 不超过 25 条。 调参方式：使用离线测试集，观测`context_recall`和接口 P95 延迟两个指标，找到业务平衡点，不能单方面追求召回率不顾线上性能。

### Q4：Rerank 能不能直接替代向量检索？为什么？

**面试回答：** 企业级生产知识库不能直接替代，只适合几十条以内极小 Demo。 原因两点：

1. Rerank 是 Cross‑Encoder，推理开销很高，如果知识库 chunk 几万几十万，全部文档和 query 组成 pair 送入 Rerank，耗时爆炸，完全达不到线上接口性能要求；向量检索 Bi‑Encoder 可以毫秒级完成海量文档粗筛。
2. 两者分工不同：向量粗召回负责从海量库里面捞出一小批潜在相关候选；Rerank 负责在这一小批候选里面做精细语义甄别。类比初试和复试，不能让全部选手直接进复试。

> 补充：Rerank 只能对已经进入候选池的文档改变排序；**上游没有召回出来的正确文档，Rerank 无法凭空生成出来。**

### Q5：Rerank 输出之后，你们为什么不用固定 TopK，而采用断崖检测动态截断？

**面试回答：** 写死固定 TopK 会出现两难：简单问题带入大量噪声，增加幻觉风险；复杂业务查询证据又不够。

我们项目 Rerank 输出文档按分数降序，采用断崖检测动态截断：最少保留 6 条，最多保留 15 条；当相邻切片分数出现**绝对差 0.5 或者相对差 25%，触发断崖截断，后面全部丢弃**，同时设置 0.3 最低安全阈值，全部低于阈值直接拒答。 简单问题自动少保留切片减少噪声；复杂问题自动保留更多有效证据。

### Q6：Rerank 之后大模型依然忽略中间高分切片，你们怎么处理？

> 原题出处：02 文档 LinkDoc 面试原题 **面试回答：** 第一，依靠 Rerank 打分，保证高相关性的切片尽量排在列表靠前的位置； 第二，Prompt 显式约束大模型逐条阅读全部参考资料，禁止只看首尾片段； 第三，配合断崖检测，过滤掉大量低分噪声，减少无关内容干扰； 必要场景可以做切片回填，把子块对应的父章节补充进上下文。

### Q7：Rerank 有哪些常见线上坑？

**面试回答：**

1. 候选集给的太大：GPU 占用高，P95 延迟暴涨，QPS 上不去；上游一定要 RRF 做候选压缩。
2. 直接硬编码全局通用分数阈值 0.5：不同 query 分数分布不一样，容易误杀有效片段或者放过噪声，需要基于业务测试集标定阈值。
3. 误以为 Rerank 可以拯救上游召回失败：正确文档没进入候选池，Rerank 无能为力。
4. 输入 Rerank 存在大量重复 chunk：浪费算力，RRF 阶段需要做文档 id 去重。
5. 直接用 Rerank 替换向量检索，知识库文档一多服务性能直接崩盘。

### Q8：RRF 已经完成排序融合了，为什么还需要再做 Rerank？

> 原题出处：01 文档知识库检索排序章节 **面试回答：** RRF 是基于**文档排名**做的粗融合算法，它并不理解 query 和文档真实语义，只利用各路召回输出的排名做计算，会存在排名靠前但是语义实际不相关的噪声文档。

Rerank 做 query‑doc 交叉编码，真正理解两者语义相关性，是整条检索链路很关键的矫正阀门。哪怕 RRF 排序不理想，Rerank 也可以把真正相关的文档拉高排序，把语义无关的文档打低分压低，为后续动态截断提供可靠分数依据。

### Q9：调参怎么验证 Rerank 相关改动是否生效？

> 原题出处：01 文档 RAGAS 评测、badcase 分析章节 **面试回答：** 不能拿少数几条 query 主观感受判断。

1. 使用固定离线测试集，调参前后跑同一套数据；重点观测`context_recall`、`context_precision`两个指标；
2. 同时关注接口 P95 延迟、GPU 利用率这类性能指标，不能只看召回效果忽略性能；
3. 观察 BadCase 集合，原有问题样本是否修复，有没有大批量新增 badcase；
4. 离线验证通过之后，再做线上小流量灰度采样，线上指标和离线结论对齐，才确认改动生效。
