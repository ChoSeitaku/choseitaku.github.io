> 📌 本文基于线上落地**StarRag企业知识库项目**实战总结，并非 Demo 玩具示例。项目面向电商产品手册场景，处理 PDF、Markdown、带图表图片的产品资料，服务内部客服、运营人员做资料问答。
> 
> 🔖 适合人群：想要做企业级 RAG 落地、面试准备大模型应用开发、想搞懂生产环境 RAG 和网上 Demo 差距的开发者。

## 前言

网上大量 RAG 教程，大多是几行代码：`PyPDFLoader`读取 PDF + 递归字符切分 + 向量库存入，直接开始问答。这种 Demo 跑本地示例没问题，但直接搬到企业生产环境会暴露出大量现实问题。

我们的**StarRag项目**，原始资料形态十分复杂：产品 PDF 手册、跨页表格、故障示意图、扫描类文档、Markdown 说明文档。直接套用 Demo 方案上线后遇到一系列痛点：

1. PDF 表格乱码，图片直接丢弃，示意图里的关键故障信息完全检索不到；
2. 切片粗暴按字符切割，把完整语义句子拦腰切断；
3. 检索返回大量无关文档，大模型幻觉频发；
4. 多轮对话用户使用代词 "这个产品怎么样"，无法识别指代的商品实体；
5. 固定 TopK 给大模型送入切片，模型更关注头部、尾部，中间有效片段直接被忽略；
6. 上线之后没有标准化评测手段，效果好坏全靠人的主观感受，缺少 BadCase 迭代闭环。

本文完整拆解一套**生产可用 RAG 完整链路**，覆盖文档导入存储链路、用户查询链路，包含解析、切片、向量化、多路召回、RRF 融合、Rerank 重排、动态截断、流式输出、评测闭环全部工程细节。

项目技术栈：`FastAPI + LangGraph + Milvus + MinerU + BGE‑M3 + BGE‑Reranker‑large + MinIO + MongoDB`

## 一、RAG 两大核心链路总览

RAG 分为**存储写入链路（文档导入）** 和**查询读取链路（用户提问）**，很多教程只讲查询链路，忽略导入链路，而导入质量直接决定最终问答效果。

### ✍️ 存储链路：文档导入流程

```
原始文件(PDF / MD)
    ↓
MinerU解析PDF，输出结构化Markdown
    ↓
VLM多模态模型解析图片，生成图片摘要
    ↓
文档清洗、表格线性化处理
    ↓
分层标题驱动切片Chunk，挂载元数据
    ↓
LLM提取商品实体item_name，回填到chunk元信息
    ↓
BGE‑M3生成稠密dense向量 + 稀疏sparse向量
    ↓
Milvus向量库批量入库
    ↓
原始文件、图片资源归档MinIO对象存储
```

### 🔍 查询链路：用户提问流程

```
用户发起提问（SSE流式接口）
    ↓
MongoDB读取历史会话上下文
    ↓
LLM完成商品名实体抽取 + 用户问题改写
    ↓
【三路并行召回】普通向量检索 + HyDE假设文档检索 + MCP网络检索
    ↓
本地两路结果执行RRF倒数排名融合、去重
    ↓
合并MCP网络检索结果，送入BGE‑Reranker‑large重排
    ↓
断崖检测动态截断候选切片集合，过滤低分片段
    ↓
组装Prompt，携带切片元数据（来源文档、标题）
    ↓
LLM生成答案
    ↓
SSE流式delta事件推送到前端，最终发送final结束事件
    ↓
用户问答会话记录写入MongoDB，用于后续评测与BadCase收集
```

> LangGraph 作为编排引擎，把导入、查询拆分为一个个可观测节点，每个节点统计耗时，方便线上排查性能瓶颈。

## 二、存储链路实战：文档解析，PDF / 表格 / 图片如何处理

> ❗ 不要直接使用`PyPDFLoader`，面对多栏排版、跨页表格、内嵌图片的工业手册，解析质量很差。

项目采用 **MinerU** 做 PDF 解析：

1. MinerU 输入 PDF，输出结构化 Markdown，自动保留标题层级、HTML 格式表格、图片引用标记；解决 PDF 文本乱序、跨页表格拆分丢失信息问题。
2. **表格处理**：MinerU 输出 HTML 表格，代码层将 HTML 表格做线性化转换，转为自然语言描述文本，保证表格内容可以被 Embedding 模型理解，否则表格数据无法有效参与检索。
3. **图片处理**：MinerU 仅输出图片引用标记，**不能读懂图片内容**。
    - 提取图片前后段落上下文；
    - 调用 VLM 多模态模型，生成图片内容摘要；
    - 图片二进制存入 MinIO 对象存储；图片摘要作为普通文本参与向量化检索；
    - 回答阶段把图片 URL 返回给前端进行渲染展示。

> 踩坑教训：如果直接丢弃图片，产品手册大量故障示意图，用户询问故障排查相关问题，知识库完全检索不到对应信息。

## 三、文档切片 Chunk 工程实践

> 面试高频：Chunk 过大 / 过小会带来什么问题；长语义超过切片最大限制如何保障语义完整性。

### 本项目落地切片策略

1. **优先按照 Markdown H1‑H6 标题层级切分**，优先尊重语义边界，拒绝粗暴字符截断；
2. 大章节内容过长，再执行递归字符切分；短的、同父标题的碎片化切片执行合并；
3. 参数配置：
    - 最大字符：`1200`，最小字符：`300`
    - 句子重叠：`overlap_sentences=1`

> 踩坑：曾经设置最大 2000 字符，发现 Reranker 对过长 Chunk 敏感度下降，关键信息被大量上下文稀释，重排打分显著变差。

4. **每个 Chunk 必须挂载完整元数据** `file_title`原始文档名、`parent_title`父级标题、`item_name`商品实体名称。 向量化拼接文本格式：`item_name + "\n" + chunk_content`。

> `item_name`可以在 Milvus 执行标量过滤，查询某一个商品时，直接过滤其他商品切片，大幅度降低检索噪声。

5. 兜底方案：当单个完整语义段落超过最大切片限制，依靠句子重叠保留上下文。进阶方案可以保存`parent_chunk_id`，命中子切片时回填父章节完整内容，本项目产品手册场景使用较少。

### Chunk 大小带来的影响总结

|Chunk 情况|带来的问题|
|---|---|
|Chunk 过大|Rerank 识别能力下降，上下文噪声变多，幻觉概率上升|
|Chunk 过小|语义碎片化，单切片信息不全，需要大量切片拼接才能得到完整信息|

## 四、向量化入库：BGE‑M3 稠密 + 稀疏混合向量

> 面试题：稠密向量、稀疏向量各自擅长什么，为什么企业项目优先做混合检索？

项目选用 BGE‑M3，同时输出**dense 稠密向量**和**sparse 稀疏向量**，Milvus 分别建立两套索引。

- **Dense 稠密向量**：擅长语义改写、同义转述；用户口语化提问，即便表述和文档不完全一致，也可以召回。
- **Sparse 稀疏向量（等效 BM25 能力）**：擅长专有名词、设备型号、参数编号这类精确关键词匹配。

> 实战经验：只使用稠密向量，设备型号、零件编号经常召回失败；只使用稀疏向量，用户口语改写的问题召回效果差。两者组合，兼顾语义和关键词，召回效果明显提升。

## 五、查询链路第一步：实体识别 + Query 改写 + HyDE

拿到用户原始 Query，**不会直接送入检索**。

1. **读取历史会话，做商品实体抽取** 多轮对话用户经常使用代词，例如 "它保修时间是多久？"。结合 MongoDB 历史对话，LLM 提取`item_name`商品实体。

- 识别成功：把`item_name`作为 Milvus 标量过滤条件；
- 识别置信度处于中间区间：反问用户确认具体产品；
- 识别置信度很低，请用户补充产品名称。

2. **Query 改写 + HyDE 假设文档检索** HyDE（Hypothetical Document Embeddings）：让大模型基于用户问题，生成一段假想的领域手册文档。将`原始query + HyDE生成文本`一起向量化检索。

✅ HyDE 价值：用户提问简短口语化，缺少领域专业术语，生成假想文档更贴合知识库行文风格，提升召回概率。 ⚠️ HyDE 风险：生成的假设文档有可能内容跑偏。

> 项目处理：HyDE 只是**一路召回来源**，不会直接当作答案；后续 Rerank 重排会过滤掉错误假设带来的噪声。

## 六、多路召回 + RRF 倒数排名融合

本项目三路召回来源：

1. 改写后 Query 普通向量检索
2. HyDE 假设文档检索
3. MCP 网络检索（补充知识库不存在的外部实时信息）

处理逻辑：

1. 前两路是本地知识库切片，使用**RRF 倒数排名融合**

\(score(d)=\sum \frac{1}{k+rank_i(d)}\) 项目中 k 取值 60。RRF 只依赖文档在各路召回结果的排名，不依赖不同检索源输出的原始分数，解决 dense、sparse 分值值域不一致的痛点。 2. RRF 完成融合去重后，再把 MCP 网页检索结果合并，统一送入 Reranker。

> 💡工程关键点：RRF 计算成本很低，先做粗融合压缩候选集合；Rerank 算力开销高，**不建议把成千上万原始候选直接丢进 Rerank**。

## 七、Rerank 重排 + 断崖动态截断：解决大模型忽略中间切片

> 面试高频：送入 Top‑5 切片给 LLM，模型只看头部尾部，中间有效信息丢失如何处理？

1. 使用`BGE‑reranker‑large`，构造 query‑doc 配对做交叉编码，输出每一个候选文档的相关性分数。
2. **放弃固定 TopK，使用断崖检测动态截断** 项目配置经验阈值：最少保留 6 条，最多保留 15 条；切片按照分数降序排列。 触发截断条件：相邻文档分数**绝对差 0.5，或者相对差 25%**，一旦触发，后面全部候选直接丢弃。

✅ 动态截断优势： 简单问题自动保留少量切片，避免噪声；复杂问题自动保留更多有效证据；规避固定 TopK 带来 "简单问题塞一堆噪声，复杂问题证据不足" 的两难。

3. 缓解大模型忽略中间片段的配套手段

- Rerank 保证高相关性切片整体排在列表靠前位置；
- Prompt 显式约束大模型逐条阅读全部参考资料，禁止只阅读首尾片段；
- 尽量不让高价值证据落到候选列表很靠后的位置。

## 八、Prompt 组装 + FastAPI SSE 流式输出

经过断崖截断过滤后的切片集合，携带元信息（来源文件名、标题）组装提示词。

提示词核心约束：

> 你的回答必须严格基于下面给出的参考资料，如果参考资料中没有对应答案，请直接如实告知用户无法回答，禁止编造、脑补任何信息。

### SSE 流式实现方案

1. 用户请求生成唯一`task_id`，后端创建内存消息队列；
2. LangGraph 执行完整 RAG 查询链路；
3. LLM 流式生成 token，每一段 delta 片段写入队列；
4. 前端请求接口`/stream/{task_id}`建立 SSE 长连接，消费队列数据；
5. 分片持续推送 delta 事件，全部生成完成推送 final 结束事件；
6. 用户提问与助手回答完整会话落库 MongoDB。

## 九、生产环境必备：评测体系与 BadCase 迭代闭环

Demo 级 RAG 写完就结束；企业 RAG 上线只是迭代的开始，必须建立评测闭环。

### 离线评测：RAGAS

重点监控 4 个核心指标：

1. `context_recall`：召回切片是否包含参考答案全部事实证据；
2. `context_precision`：召回结果噪声占比；
3. `faithfulness`：答案是否忠实于上下文，衡量幻觉程度；
4. `answer_relevancy`：回答内容是否贴合用户原始问题。

### BadCase 两条收集渠道

1. **用户端**：前端提供 "答案无帮助" 反馈按钮，用户点击直接记录当前 query、召回切片、模型输出；
2. **日志采样**：线上采样，RAGAS 打分较低的样本自动归入 BadCase 库。

### BadCase 标准排查步骤

1. 确认原始知识库文档中本身是否存在答案；
2. 顺着链路查看日志：Embedding 得分 → RRF 融合输出 → Reranker 打分；
3. 定位根因：文档解析问题 / Chunk 切片问题 / 召回问题 / Rerank 过滤 / Prompt / 模型生成问题；
4. 根据根因迭代：调整切片策略、调参召回阈值、优化提示词、补充修正知识库文档。

## 十、项目踩坑复盘（真实生产遇到问题）

1. ❌ 直接 PyPDFLoader 读取 PDF → 表格、图片信息丢失 ✅ 改用 MinerU 解析 PDF，VLM 生成图片摘要
2. ❌ Chunk 一味设置很大，企图减少分片数量 → Rerank 敏感度下降，关键信息被稀释 ✅ 控制最大 1200 字符，优先按标题层级切分
3. ❌ 只使用 dense 稠密向量，设备型号、专有名词召回失败 ✅ BGE‑M3 同时开启稠密 + 稀疏混合检索
4. ❌ 写死固定 TopK，简单问题噪声多，复杂问题证据不足 ✅ 断崖检测动态截断候选切片
5. ❌ HyDE 生成内容跑偏，直接作为上下文输入模型 ✅ HyDE 仅作为一路召回，交给 Rerank 过滤噪声
6. ❌ 多轮对话代词指代识别失效 ✅ 读取历史会话，实体抽取，Milvus 标量过滤
7. ❌ 上线无评测，效果好坏靠主观感受 ✅ RAGAS 离线评测 + BadCase 收集闭环

## 十一、Demo 玩具 RAG VS 生产级企业 RAG 对比

|对比维度|Demo 玩具 RAG|StarRag生产 RAG|
|---|---|---|
|文档解析|PyPDFLoader 简单读取|MinerU 解析 PDF + VLM 图片摘要 + 表格线性化|
|切片策略|粗暴固定字符切分|标题优先分层切片，携带完整元数据|
|向量能力|仅稠密 dense 向量|BGE‑M3 稠密 + 稀疏双向量混合检索|

## 面试高频追问

**Q1：RAG 上线之后召回效果突然变差，你的排查思路？**

> 优先拆解整条链路每一个节点耗时与输出日志：文档解析→切片→Embedding 打分→多路召回→RRF 融合→Rerank 打分。确认是解析、切片、向量、召回、重排哪一层出问题，结合 BadCase 看是候选集变少，还是高分候选被过滤，再针对性调参或者修改知识库。

**Q2：HyDE 什么场景会起到反效果？**

> 用户问题领域知识极度冷门，HyDE 生成大量虚假假设文档；如果没有后续重排过滤，虚假文档混入候选集合带来幻觉。对策：HyDE 只作为一路召回，不能作为唯一召回来源。

**Q3：Rerank 能不能直接替代多路召回？**

> 不建议。Rerank 计算开销大，如果把上万条原始候选全部送入 Rerank，QPS 会急剧恶化。工程最佳实践：多路召回 + RRF 做廉价粗筛，压缩候选数量，再送入 Rerank 精排。

**Q4：大模型忽略中间切片，除了调整 Rerank，还有哪些手段？**

> 1. 提示词强制模型逐条阅读参考资料；2. 优化切片，尽量让关键证据分数拉高排到前面；3. 必要时做切片回填，把子块对应的父章节补充进上下文。

**Q5：为什么生产环境继续选用 BGE‑M3，而不用更新的向量模型？**

> 选型不只看榜单分数，要综合考量：模型推理速度、显存占用、稠密稀疏双输出能力、开源生态、线上稳定性、业务场景适配，更新模型不一定在自己业务数据集表现最优，需要自己的业务测试集做对比验证。

**Q6：向量库选型，Milvus、Qdrant、ES 怎么选？你们项目为什么选择 Milvus？**

> - ES：擅长全文 BM25 检索，向量能力属于附加能力，大规模向量场景性能弱；
> - Qdrant：适合中小型项目单点部署，上手简单；
> - Milvus：企业级向量库，支持存算分离，支持分布式部署，支持 dense/sparse 双索引，适合文档数量比较大的业务场景。
>
> 我们StarRag项目文档规模几千份，chunk 几十万级别，需要同时支持稠密稀疏向量，未来存在扩容需求，所以选用 Milvus。

**Q7：什么场景 RAG 效果差？RAG 的局限性是什么？**

> 1）知识库完全不存在该问题对应的事实，RAG 无法凭空生成答案；2）问题需要跨大量切片做深度多步推理，切片证据分散；3）文档质量差：文档乱码、残缺、图片没有生成摘要；4）用户问题极度冷门，HyDE 生成大量虚假假设，带来噪声。
>
> 局限的解决手段：
> - 知识库缺失事实：可以接入 MCP 联网检索作为补充；
> - 证据分散：切片回填父章节、知识图谱辅助；
> - 文档质量差：优化解析链路，清洗原始文档。

**Q8：PDF 文档你们是如何解析的？MinerU 解决什么问题？**

> 我们项目没有直接使用 PyPDFLoader，PyPDF 对多栏 PDF、跨页表格、内嵌图片的工业手册解析效果很差。我们采用 MinerU 做 PDF 解析，把 PDF 转为结构化 Markdown，可以保留标题层级、表格 HTML 标签、图片引用。MinerU 解决三大痛点：1）多栏 PDF 文本乱序问题；2）跨页表格拆分丢失内容；3）提取图片占位标记。
>
> 但是 MinerU **只能提取图片引用，不能看懂图片内容**。所以我们会拿到图片前后的上下文，调用 VLM 多模态模型生成图片摘要；原始图片存入 MinIO 对象存储，图片摘要文本参与向量化检索；回答的时候把图片 URL 返回前端渲染。
>
> 补充踩坑：最开始直接丢弃图片，产品手册大量故障示意图，用户问故障排查完全检索不到，后面补充 VLM 生成摘要才解决。

**Q9：文档切片 Chunk 怎么做？chunk 过大、过小分别会有什么问题？同一个段落语义超过最大 chunk 长度，如何保证语义完整？**

> 我们StarRag项目切片策略优先按照 Markdown H1‑H6 标题层级切分，优先保证语义边界；大章节过长再递归字符切分，短的同父标题切片做合并。参数配置：最大 1200 字符，最小 300 字符，句子重叠 overlap_sentences=1。每个 chunk 都会挂载元数据：`file_title`文档名、`parent_title`父标题、`item_name`商品名实体，向量化拼接`item_name + "\n"+chunk_content`，后续查询可以做标量过滤。
>
> - Chunk 过大：reranker 对长片段敏感度下降，关键信息被噪声稀释，幻觉概率上升；我们之前设置 2000 字符就踩过这个坑。
> - Chunk 过小：语义碎片化，单块信息不全，需要大量切片拼接。
>
> 如果完整语义段落超过最大 chunk：1）优先依靠句子重叠保留相邻上下文；2）进阶方案：保存`parent_chunk_id`，命中子切片回填父章节；本项目手册文档场景该方案使用不多。

**Q10：稠密向量 dense 和稀疏向量 sparse 分别擅长什么，为什么项目要做混合检索？**

> 项目使用 BGE‑M3，可以同时输出 dense 稠密向量与 sparse 稀疏向量。1）稠密 dense 向量：擅长语义改写、同义转述；用户口语化提问，哪怕表述和文档不完全一致，也能召回相关内容。2）稀疏 sparse 向量，等价 BM25 能力：擅长专有名词、设备型号、参数编号这类精确关键词匹配。
>
> 只使用 dense：型号、零件编号经常召回失败；只使用 sparse：用户口语改写的问题召回效果差。所以生产环境我们两路同时检索，兼顾语义理解和关键词精确匹配，召回效果会明显提升。Milvus 中为两套向量分别建立索引。

**Q11：什么是 HyDE？HyDE 有什么缺点？什么场景会降低效果？HyDE 生成内容跑偏如何处理？**

> HyDE 全称 Hypothetical Document Embeddings，假设性文档检索。原理：根据用户原始问题，让大模型生成一段假想的领域文档，把原始 query + 假想文档一起向量化进行检索。
>
> ✅优点：用户提问很短、口语化、缺少领域术语，假想文档更贴合知识库行文风格，提升召回。
>
> ❌缺点 & 失效场景：如果用户问题领域非常冷门，大模型会生成完全虚构的假设文档，带来虚假候选，反而引入噪声，降低检索效果。
>
> 我们项目处理手段：HyDE 仅仅是**其中一路召回来源，绝对不作为答案来源**。生成出来的假想文档对应的候选，会和普通向量检索结果一起进入 RRF 融合，再交给 Rerank 重排过滤噪声，就算 HyDE 跑偏，重排阶段也可以把低分的错误候选过滤掉。

**Q12：什么是 RRF 倒数排名融合？为什么不直接把全部候选丢进 Rerank？**

> RRF 全称 Reciprocal Rank Fusion，倒数排名融合。公式：\(score(d)=\sum \frac{1}{k+rank_i(d)}\)，我们项目 k 取 60。它不依赖各路检索输出原始分数，只依靠文档在每一路召回的排名做综合打分，解决 dense、sparse 两路向量分数值域不一致，无法直接相加的问题。
>
> 为什么不全部候选直接丢 Rerank：Rerank 交叉编码算力开销很高，如果把上万候选全部送入 Rerank，QPS 会急剧下降，服务延迟会爆炸。工程最佳实践：多路召回 → RRF 做廉价粗融合、去重，压缩候选集数量，压缩完成之后再送入 Rerank 做精排。我们项目中普通向量、HyDE 两路本地知识库结果走 RRF，之后再合并 MCP 网络检索结果送入重排。

**Q13：Rerank 之后返回 top‑N 给大模型，但大模型更关注头部和尾部，中间切片容易丢失，你们项目怎么解决？**

> 这个是真实生产非常常见的问题，我们项目没有写死固定 TopK，使用**断崖检测动态截断策略**。
>
> 1）BGE‑Reranker‑large 输出每一个候选的相关性分数，文档按分数降序；2）配置经验阈值：最少保留 6 条，最多保留 15 条；当相邻切片分数出现**绝对差 0.5 或者相对差 25%，触发断崖截断，后面全部丢弃**。
>
> 好处：简单问题自动保留少量切片，减少噪声；复杂业务问题自动保留更多证据切片，规避固定 TopK 的两难。
>
> 除此之外配套三种手段缓解中间片段丢失：1）依靠 Rerank 打分，保证高相关性切片尽量排在列表靠前；2）Prompt 显式约束大模型，要求逐条阅读全部参考资料，禁止只看首尾；3）必要场景做切片回填，把子块对应的父章节补充进上下文。

**Q14：你们多轮对话代词指代怎么解决？比如用户问 "它的保修期多久？"**

> 我们会读取 MongoDB 保存的历史会话，交给 LLM 做商品名实体抽取，从上下文识别代词指代的`item_name`。
>
> - 识别置信度高：拿到商品名，直接作为 Milvus 的标量过滤条件，只检索该商品的 chunk，过滤掉其他商品文档；
> - 置信度中等：反问用户确认是哪一款产品；
> - 置信度很低：提示用户补充产品名称。
>
> 识别成功之后，商品名实体还会回填会话记录，后续多轮对话直接复用。

**Q15：SSE 流式响应你们项目是怎么实现的？为什么选择 SSE 而不用 WebSocket？**

> 基于 FastAPI 实现，流程：1）用户发起请求生成唯一 task_id，后端创建内存消息队列；2）LangGraph 后台执行完整 RAG 查询链路；3）LLM 流式生成 token，每一段 delta 片段写入队列；4）前端访问`/stream/{task_id}`建立 SSE 长连接消费队列；5）不断推送 delta 事件，全部生成完毕推送 final 结束事件。
>
> 选择 SSE 原因：SSE 基于 HTTP，单向服务端推送给客户端，浏览器原生支持，自带断线重连。我们业务场景是用户提交问题之后后端持续输出答案，不需要客户端高频往服务端发送消息，不需要双向通信。WebSocket 适合双向高频交互，会增加开发维护成本，本场景收益不大。

**Q16：RAG 怎么评测？RAGAS 看哪些核心指标？线上 BadCase 怎么收集和排查？**

> 分为离线评测和线上闭环。
>
> **离线评测使用 RAGAS，重点 4 个指标：**
> 1. `context_recall`：召回切片有没有包含参考答案全部事实；
> 2. `context_precision`：召回结果噪声多少；
> 3. `faithfulness`：答案是否忠实上下文，衡量幻觉；
> 4. `answer_relevancy`：回答和用户原始问题是否相关。
>
> **BadCase 两条收集渠道：**
> 1）用户端：前端提供 "答案无帮助" 反馈按钮；2）日志采样：线上采样，RAGAS 打分低的样本自动存入 badcase 库。
>
> **标准排查步骤：**
> 1. 确认原始知识库文档本身有没有答案；
> 2. 顺着链路看日志：文档解析 → chunk 切片 → embedding 打分 →多路召回 → RRF 输出 → Rerank 打分；
> 3. 定位根因：解析 / 切片 / 召回 / 重排 /prompt/ 模型生成；
> 4. 根据根因迭代：调整切片、调参阈值、优化 prompt、补充知识库文档。

**Q17：RAG 上线之后响应从 3s 突升到 12s，如何排查耗时？**

> 我们项目基于 LangGraph 编排，每一个节点都会打印耗时日志，可以快速定位瓶颈。RAG 链路主要耗时点：1）LLM 大模型调用（改写、生成答案）；2）MCP 联网搜索网络 IO 阻塞；3）Embedding、Rerank 推理；4）向量库检索。
>
> 排查步骤：1）查看各个节点埋点耗时日志，定位到底哪个节点耗时暴涨；2）复现问题，对比正常和异常请求的入参；3）针对瓶颈做降级优化，例如 MCP 搜索超时直接跳过网络检索，只使用本地知识库结果兜底。

---

> 📝 写在最后 企业级 RAG 的难点，**并不在于调用大模型做生成，而在于前面整条预处理、检索、排序链路的工程化**。很多时候答案已经存在知识库，但是解析、切片、召回某一步出错，大模型再强大也拿不到正确证据，幻觉自然就出现。
> 
> 真正的生产 RAG，是一整套可控、可观测、可迭代的工程系统，而不是几行 Notebook 示例代码。
